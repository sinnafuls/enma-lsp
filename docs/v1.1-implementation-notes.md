# Enma v1.1 — LSP implementation notes

**Status:** Tier 1 (tokenizer) shipped. Tiers 2-5 pending Tier 0 spec resolution.

## Spec source

The Enma language SDK is **not public** as of 2026-05-08 (per `pcx-extended-api/00-overview.md` overview: "Perception's Enma SDK is not public yet"). The authoritative source for v1.1 features in this LSP is the **release-notes message** from the language developer, captured verbatim below for traceability.

> **scripting**
> Value semantics now match C++. Passing a struct by value is a true copy — mutations don't leak back to the caller. Use `T&` / `T*` when you actually want callee mutation.
>
> **Way more overloadable operators on your types:**
> - Bitwise/shift `& | ^ << >>`, compound `+= -= *= /= %= &= |= ^= <<= >>=` (auto-falls back to `a + b` if only `+` is defined)
> - Unary `~ ! *` (smart-pointer-style deref), prefix/postfix `++ --` separately (`T operator++()` vs `T operator++(int)`)
> - `operator()` for callable types, `operator->` (works for member access **and** method calls now)
> - `operator T()` conversion — now fires implicitly in var-init, fn args, returns, **and** arithmetic
> - Copy ctor `T(const T&)`, move ctor `T(T&&)` (via `move(a)`), `operator=`, `operator<=>` (auto-derives all six comparisons)
>
> **Math types** (vec2/3/4, quat, mat4) got the full operator set: `+= -= *=` (Hamilton/matrix product where applicable), `!v`, `cast<bool>(v)`, copy-assign. mat4 also gained `+ - ==` and unary `-`.
>
> **Numeric literals:** `0b1010` binary, `1_000_000` underscore separators (works in hex/float/exponent too: `0xFF_FF`, `1_234.567_8`, `1_000e3`). UDLs still work: `1_500_km`.
>
> **New syntax:**
> - Trailing return: `auto add(int64 a, int64 b) -> int64 { ... }`
> - Uniform init: `P p = P{1, 2}` in expression contexts
> - Designated init in `T{...}`: `Vec3i{.x = 1, .y = 2, .z = 3}` (out-of-order ok)
> - C++17 if-init: `if (auto r = f(); r > 0) { ... }`
> - `enum class` / `enum struct`, `friend`, `final`, `virtual` keywords accepted
> - Namespace-qualified ctors: `ns::Inner(args)`, multi-level too
> - `constexpr` struct/array literals — nested structs, arrays of structs, nested arrays, all fold at compile time
> - `new T[N]` contiguous arrays with per-element ctor/dtor

### Surface-syntax interpretation decisions

The release notes are unambiguous on surface syntax. The following decisions are recorded for spec traceability:

1. **Digit separator rule:** `_` is consumed as a separator iff it is followed by a digit valid for the current numeric base. This naturally handles `1_000` (separator), `42_km` (UDL — `k` is not a digit), `1_` (separator not consumed because no following digit), `1__2` (second `_` not consumed because `_` is not a digit). The rule is inspired by C++23 / Rust / Python conventions and aligns with the release-notes example `1_500_km` (separator inside `1_500`, then UDL `_km`).
2. **Binary literal:** `0b` prefix, only `0`/`1` digits, supports separators (`0b1010_1010`). No mention of `0o` octal in the release notes — not implemented.
3. **`<=>` precedence:** added to `MULTI_CHAR_OPERATORS` array in longest-match order. Parser-level precedence wiring is **Tier 2** scope; the tokenizer just emits the token.
4. **Numeric value for binary:** `parseNumber()` in `parserPreprocess.ts` parses `0b...` via `parseInt(_, 2)` after stripping separators. Original `text` field on `TokenNumber` retains the source representation (with `_`) so hover / display preserves what the user typed.

## Tier 0 — open questions blocking Tiers 2-5

The release notes describe behavior, not formal grammar productions. Before parser/analyzer work begins, these need resolution from the language dev (or a public spec):

1. **`enum class` scoping:** does it introduce a new scope barrier (members not leaked) or is it tag-only?
2. **`mat4 operator==`:** epsilon-tolerant or strict bitwise?
3. **`delete[]` analyzer rule** pairing with `new T[N]`: required or optional?
4. **Designated init mixing:** can positional + designated members mix in one `T{...}` init list?
5. **`move(a)` invalidation in legacy mode:** does the spec require a use-after-move warning even in legacy, or full silence?
6. **`operator->` chain depth limit:** is there a max before "infinite chain" warning?
